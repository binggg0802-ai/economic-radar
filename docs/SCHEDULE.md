# 自動更新排程方案

原則：

- **cron 只負責叫醒，要不要連線由 `pipeline/lib/schedule.mjs` 判斷。**
- 不假設資料在固定時間一定公布。
- 取得當期資料後就停止重抓。
- 官方日程未核對的，不排程。

## 時區、假日、延遲

- 所有時間以 `+08:00` 儲存；美東時間用 `Intl` 換算，不寫死時差。
- 證交所休市日表每次執行都更新，取得失敗時使用上次保存版本，並在驗證結果中註明。
- 補行交易日（週六交易）由週末喚醒處理。
- GitHub 排程可能延遲或略過：避開整點、多次喚醒，前端以 `valid_until` 把漏跑顯示為「資料逾期」。
- 同時觸發：`concurrency` 群組讓同一時間只有一個執行，第二個排隊。

**結論**：證交所 OpenAPI 的盤後資料**至少晚於 18:10 才更新**，實際時間尚未測得，可能是晚間或隔日上午。

**建議**（不臆測時間，用實測決定）：

1. 正式排程啟用後，先把檢查時段延長到 21:47，隔日 07:07–09:07 再補抓。
2. 逾期門檻暫定為「下一交易日 09:00」，也就是開盤前仍沒有前一交易日收盤才算逾期。
3. 收集 5～10 個交易日的「首次取得時間」後，再把門檻與排程定案。
4. 若要當天 14:00 後就顯示收盤，需要改用證交所網站資料（使用條款禁止未經同意的爬蟲，需取得同意）或付費資訊源，兩者都要你決定。

## 修正後的規則（2026-11-11 晚間，已上線於 main）

### 狀態判斷

依「交易日 → 休市日 → 官方實際取得紀錄」判斷，不用固定時間。

- 令 M ＝ 已保存最新資料日之後的下一個交易日。休市日依證交所 holidaySchedule；「市場無交易，僅辦理結算交割」的日子也不算交易日。
- **已更新**：M 尚未收盤，代表手上的資料就是最新收盤。
- **尚未公布**：M 已收盤（13:30 後），但現在還沒超過期限＝M 之後下一個交易日的 09:00。這是正常等待，**不是失敗**。
- **資料逾期**：超過上述期限仍沒有 M 的收盤。
- **更新失敗**：連線失敗或 HTTP 錯誤。保留最後一次成功驗證的值與原始日期。
- **來源異常**：官方有回應，但內容異常（格式改變、驗證不過、回傳比已保存更舊的日期），不發布。
- **從未成功取得**：沒有任何驗證過的值，不給數字。

為什麼期限是「下一交易日 09:00」：

- 實測證交所 OpenAPI 到 18:10 仍未更新當日收盤。
- 09:00 開盤前仍沒有前一交易日的收盤，才確定是異常。
- 這是暫定值，啟用排程後會依 data 分支 `history` 的 `first_seen_at`（首次取得時間）累積 5～10 個交易日再調整。

### cron（UTC），由 schedule.mjs 決定是否真的連線

| cron | 台北時間 | 目的 |
|---|---|---|
| `7,27,47 6-10 * * 1-5` | 週一～五 14:07–18:47，每 20 分鐘 | 收盤後檢查 |
| `7 11-15 * * 1-5` | 週一～五 19:07–23:07，每小時 | 實測 OpenAPI 晚間才更新 |
| `7,37 23 * * 0-4`、`7,37 0 * * 1-5` | 週一～五 07:07–08:37 | 09:00 期限前補抓 |
| `17 7 * * 0,6` | 週六、日 15:17 | 補行交易日、對帳 |

已取得最新收盤時，排程叫醒後直接略過，不連線。略過也會寫執行紀錄，作為心跳。

### 排程延遲與漏跑

- GitHub 排程可能延遲或略過。每次執行都會記錄 `github.event.schedule` 與實際啟動時間，啟用後可計算延遲。
- 多次叫醒＋以期限判斷，單次漏跑不影響結果。
- 如果排程整個停擺，前端以 `valid_until` 判定「資料逾期」，不會誤標最新。

### 通知

| 事件 | 通知方式 |
|---|---|
| 更新失敗、來源異常、從未成功取得 | 該次 Actions 失敗（紅燈），GitHub 寄失敗通知給最後修改排程的人 |
| 連續 3 次失敗、來源異常、資料逾期 | 自動開 GitHub Issue（標籤 data-alert），watch 此 Repository 的人會收到 Email；狀態改變才留言，避免洗版 |
| 恢復 | 自動關閉 Issue |
| 演練 | 開「【演練】」Issue 後立即關閉，data 分支不寫入 |
